# Контекст проекта

## О проекте

Дипломный проект: **интернет-магазин средней сложности на Python + Django** с
интеллектуальными модулями на основе языковых моделей.

Основа — рабочий прототип (бывшая курсовая). Задача диплома — развить его:
закрыть технический долг, расширить функционал и добавить AI-модули.

**Автор:** Шевырев Дмитрий Сергеевич, КубГУ, ФКТиПМ, 3 курс.
**Репозиторий:** https://github.com/DmitriyShevyrev/kursovoi_project

## Стек и окружение

- **ОС разработчика:** Windows. Все команды/пути — под Windows (PowerShell/CMD).
- **Python 3.13, Django 6.0.4**, архитектура MTV.
- **БД:** PostgreSQL 18 (драйвер psycopg 3). SQLite остался в прошлом.
- **Фронтенд:** Django-шаблоны + Bootstrap 5 (через CDN). Без React и JS-фреймворков.
- **AI:** `sentence-transformers` (локально, для поиска) + Gemini Flash free API
  (генеративные задачи). Всё через абстрактный слой-провайдер.

Виртуальное окружение лежит внутри проекта: запускать через `venv\Scripts\python.exe`.

## Структура (4 приложения)

- `catalog` — товары, категории, карточки, поиск, фильтрация. Модели: Category,
  Product, ProductImage.
- `cart` — корзина на сессиях + синхронизация в БД через signals. Модели: Cart, CartItem.
- `orders` — оформление, статусы, история, отмена заказов. Модели: Order, OrderItem.
- `users` — регистрация, авторизация, личный кабинет. Модель: Profile.
- `config` — настройки проекта, корневые urls.

Особенности: корзина двухуровневая (SessionCart + БД, синхронизация через signals);
цена фиксируется в OrderItem на момент покупки; Profile создаётся автоматически
через signals; поиск сейчас через `icontains`.

## Данные и воспроизводимость

Ни база, ни секреты в репозитории не хранятся. Разворачивание с нуля:

**1. Создать роль и базу.** В pgAdmin (Query Tool) или psql — по одной команде за раз:

```sql
CREATE ROLE kursovoi_user WITH LOGIN PASSWORD 'пароль' CREATEDB;
CREATE DATABASE kursovoi OWNER kursovoi_user ENCODING 'UTF8';
```

Выполнять их вместе нельзя: pgAdmin оборачивает выделенный текст в транзакцию,
а `CREATE DATABASE` внутри транзакции запрещён — откатится и роль тоже.
Право `CREATEDB` нужно тестам: Django создаёт временную базу `test_kursovoi`.

**2. Заполнить `.env`.**

```
copy .env.example .env
venv\Scripts\python.exe -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
:: полученный ключ вписать в SECRET_KEY, пароль роли — в DB_PASSWORD
```

**3. Развернуть схему и каталог.**

```
venv\Scripts\python.exe manage.py migrate
venv\Scripts\python.exe manage.py loaddata catalog.json
venv\Scripts\python.exe manage.py createsuperuser
```

Без `.env` проект намеренно падает с ошибкой `SECRET_KEY not found`: запасного
значения в коде нет, чтобы секрет не мог снова утечь в репозиторий.

Фикстура `catalog/fixtures/catalog.json` содержит 5 категорий и 52 товара.
Картинки к ним лежат в `media/products/` и **не игнорируются** — без них
каталог после клонирования показывал бы пустые карточки.

При пересоздании фикстуры нельзя использовать флаг `-o`: Django открывает файл
в кодировке Windows (cp1251) и падает на символе `²`. Вместо этого:

```
set PYTHONIOENCODING=utf-8
venv\Scripts\python.exe manage.py dumpdata catalog --indent 2 > catalog\fixtures\catalog.json
```

Та же ловушка с кодировкой: `curl` в Git Bash отправляет кириллицу в запросе
не в UTF-8, из-за чего поиск «ничего не находит». Проверять поиск нужно из
Python (`urllib`) или в браузере, а не через `curl`.

## Логирование

Настройка — в `config/settings.py`, блок `LOGGING`. Логи пишутся в `logs/django.log`
(каталог игнорируется git). Ротация: файл до 5 МБ, хранится 5 предыдущих копий.

**В лог не попадают персональные данные.** Пишутся только идентификаторы:

```
INFO  orders.views — Заказ создан: order_id=1 user_id=2 позиций=1 сумма=8990.00
WARN  users.views  — Неудачная попытка входа
WARN  cart.signals — Позиция корзины пропала при входе: product_id=7 user_id=2
```

Лог — такое же хранилище ПДн, как БД, но его легко скопировать или случайно
закоммитить, а средств защиты у него нет. Поэтому ни ФИО, ни адреса, ни логины,
ни IP-адреса в него не пишутся (152-ФЗ, принцип минимизации). Из-за отказа от
логина и IP запись о неудачном входе безлика, зато подбор пароля всё равно
заметен по частоте таких строк.

Запрет закреплён тестами `orders.tests.OrderLoggingTests`: они оформляют заказ
на вымышленного «Петра Незабудкина» и проверяют, что в логе есть `order_id`,
но нет ни фамилии, ни адреса. Тесты проверены на живучесть — при подсунутой
утечке падают.

## Приватность (проектное требование)

Персональные данные клиентов (реальные ФИО, адреса, телефоны) **не отправляются
во внешние LLM**. В облачные модули идут только данные каталога и обезличенный
текст (принцип минимизации ПДн, 152-ФЗ). Провайдер сменный: возможен переход на
локальную модель без изменения кода модулей.

**Этап 8 — Тестирование и метрики.**
